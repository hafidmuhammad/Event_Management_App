name: email-management
description: Use for event-scoped email templates, the Gmail-style compose window, recipient JSON, content blocks, safe rendering, previews, and broadcasts.
---

- Templates use `email_templates.recipient_json` and versioned `content_json`.
- `content_json.deliveryStatus` can be DRAFT or READY. New templates start as DRAFT. Explicit drafts and legacy names prefixed with [DRAFT] cannot broadcast or send automatic email; changing status never sends mail. Legacy templates without this field retain their previous delivery behavior.
- Create and edit use the full-screen Gmail-style compose window (`ComposeWindow` / `ComposeTrigger`), not the centered `ModalTrigger`. It opens full screen and offers minimize, restore-to-docked, and close. Children stay mounted across window states so an in-progress draft is never lost. Closing a dirty window asks for confirmation.
- Compose layout order (top to bottom): Details row (Template name, Email type, Status Draft/Ready, always visible), Recipients (To segment, Contacts picker, manual Emails chips, optional Cc/Bcc), Subject, message toolbar (Undo, Redo, Insert, Preview, and "From library" at the right end), block editor, then the sticky footer with the save status and Save template. Status is owned by `TemplateForm` and passed to `EmailBuilder` as `deliveryStatus`; it is still stored inside `content_json`.
- Recipients are chip based. Enter, comma, semicolon, or Tab commits an address; Backspace on an empty field removes the last chip; invalid addresses stay in the field and are announced instead of being dropped.
- Live preview is a toolbar button that opens a modal, never a side-by-side pane. The preview paper is always light because that is how mail clients render; its slate/white classes are intentional and must not be tokenized.
- `recipient_json` carries `to.contactListIds`, `ccContactListIds`, and `bccContactListIds`. Global contact lists are additive: they extend the event segment rather than replacing it. CUSTOM requires either a manual address or a contact list.
- `resolveRecipients` accepts unparsed recipient input and parses it, so older stored JSON without the contact-list fields still resolves.
- Broadcast builds synthetic rows for addresses with no participant record (custom lists and global contacts) so they still receive a personalized message.
- Resolve and validate button links after variable substitution. Ticket paths become absolute URLs. QR rendering uses the original resolved value (not HTML entities) and configured size.
- Recipient participant segments are always scoped by event; approved includes checked-in participants.
- Renderer escapes participant variables and rejects unsafe button URLs.
- Button blocks support the resolved `{{event.registration_url}}` customer registration form link, `{{ticket.url}}`, and custom HTTPS links.
- Image blocks show the uploaded image in the builder and provide a small remove control to return to the image URL/upload field.
- Broadcasts must resolve recipients individually and never expose other recipients.
- Mail delivery uses SMTP only when `MAIL_TRANSPORT=smtp`; `MAIL_TRANSPORT=preview` (the default) writes local HTML previews. SMTP settings come from server-side environment variables and Office 365 uses SMTP AUTH with STARTTLS on port 587.
- `src/services/email.ts` renders email HTML and is the only file allowed to keep hardcoded hex colors, because Outlook and Gmail do not support CSS variables.
- Paragraph runs support structured bold/italic/underline/inline links and bullet/number lists. A link is an absolute HTTP(S) address or one placeholder such as `{{event.registration_url}}` or `{{ticket.url}}`, resolved per recipient at render time (`/t/...` ticket paths become absolute). The paragraph editor shows a Gmail-style floating toolbar above selected text (Bold, Italic, Underline, Link; Ctrl+B/I/U/K). The Link panel offers "Registration form" and "Ticket link" buttons plus a free address field. Raw pasted HTML is not persisted; text and variables remain escaped. Undo/redo is bounded to 50 message-body snapshots; blocks have drag grips and accessible reorder arrows.
- Draft recovery uses local storage scoped by event/template, with an explicit restore modal. Autosave never broadcasts or marks a template ready.
- Applying a global template replaces only the subject and body of the draft and re-mounts the form; the configured recipients are preserved. "Save to library" copies subject and body into the global library and never copies recipients.
- Broadcast history and up to 100 latest delivery records are event-scoped. PREVIEW is a saved local preview, never SENT; RUNNING/PENDING may indicate interruption and must be reviewed before retrying. Mail transport is mocked in report integration tests.
- Send Test requires an application confirmation modal, uses the real event variables, records delivery, and returns only mode (not private local preview paths).
- Send Test is offered only to ADMIN and EVENT_MANAGER. The API returns 401 for a missing/expired session and 403 for an authenticated role without permission; the UI offers sign-in recovery for 401. RECEPTIONIST can preview email without a Send Test control and does not load global library data.

## Sending, status and reminders

- The Insert menu is grouped: Content (Text, Heading, Image, Table, Divider, Spacer) and Links and actions (Registration form button, Ticket button, Button with other address, Ticket QR code). Button blocks pick their target from a "Link to" select (Registration form, Ticket page, Other web address); the address field only shows for the last one.
- Each template card has at most two visible actions. Managers see `[Send] [Edit] [...]` (menu: Preview and send test, Save to library); a receptionist sees only Preview. `TemplateCardActions` owns the Preview, Send and Edit windows so they survive the menu closing; `ComposeDialog` is the controlled compose window (`ComposeTrigger` wraps it).
- Send always opens a review window: subject sample, To/Cc/Bcc counts, delivery mode. A Draft template shows "Mark as ready" (`markTemplateReadyAction`, which only flips `deliveryStatus`, strips a legacy `[DRAFT]` name prefix, and never sends). With no recipients it offers "Edit recipients". Otherwise it shows the confirm checkbox and the confirmed broadcast button.
- Scheduled reminders live in `email_schedules` (template, `offset_minutes` before `events.event_start`, status PENDING/RUNNING/SENT/FAILED/SKIPPED). The send time is never stored: it is `event_start - offset`, so moving the event moves its reminders. Offsets are 5 minutes to 90 days; the same template cannot have two reminders at the same offset.
- `runDueSchedules()` (src/services/email-schedules.ts) claims each due reminder with a conditional update (PENDING -> RUNNING), then calls `broadcastTemplate`. A draft template or a draft event leaves the reminder PENDING ("Waiting for Ready"); a cancelled/finished event, or one that already started, marks it SKIPPED. RUNNING that never finishes means the process stopped mid-send: check the delivery report before retrying.
- Something must call the runner: `pnpm reminders:run` (every ~5 minutes from Windows Task Scheduler or cron) or `POST /api/cron/email-reminders` with `Authorization: Bearer $CRON_SECRET`. Without `CRON_SECRET` the endpoint answers 503.
- "Use 3-step scheme" creates three draft REMINDER templates (7 days, 1 day, 3 hours before) with their schedules; running it again creates nothing new. Templates only send after they are marked Ready.
- Reminder UI is limited to ADMIN and EVENT_MANAGER; `removeScheduleAction` refuses RUNNING reminders.
